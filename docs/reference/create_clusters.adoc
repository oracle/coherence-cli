== Creating Clusters

=== Overview
Create, start, stop and scale local development clusters, then manage them using the usual CLI commands.

These commands allow you to create local only development based clusters (scoped to localhost) for Coherence CE 22.06.x and
Commercial 14.1.1.2206.x versions and above. You must have the following setup for this to work:

1. A Coherence-compatible Java executable on the PATH. CE 22.06.x uses Java 11 or later;
commercial 14.1.1.2206.x requires Java 11.0.15 or later. CE 22.09 through 25.09 require Java 17 or later.
The 14.1.2 and 15.1.1 lines document Java 17 and 21. Check the selected release's certification policy;
passing a minimum-version check does not certify every newer JDK, platform or custom dependency.
2. Maven 3.6+ or JDK compatible Gradle version 7.+ executable on the PATH.

NOTE: Maven is used by default for dependency resolution and classpath generation, but if you prefer Gradle, then use the
following: `cohctl set use-gradle true`. You can revert to Maven by using `cohctl set use-gradle false`.

Once you create a local cluster, you can manage and monitor these clusters in the same way as you can with discovered
or manually added clusters. You can also run the Coherence console and CohQL (Query client) against these clusters.

=== Management defaults

When you create a cluster, the first node started will always have management over REST enabled.
Management REST binds to `127.0.0.1` by default. The JDK remote JMX connector is disabled unless you select
a positive `--jmx-port`; when enabled, both its registry and RMI connector bind to loopback by default.
WKA controls cluster discovery and does not select management addresses.

These endpoints have no authentication or encryption. Other users on the same host can access loopback endpoints.
Metrics and health HTTP listeners, cluster transports, proxies and listeners created by user code are separate surfaces;
the management bind flags do not restrict them.
These management controls apply to the stock JDK and Coherence management configuration.
The selected runtime, installed defaults, user code, agents and resources are trusted inputs. Custom startup classes,
operational overrides, replacement management resources/providers and agent-created listeners need a separate review.

You may also select a saved JVM profile with `-P profile-name`. See <<set-profile,Set Profile>> and
<<advanced-jvm-options,Advanced: JVM options and trusted inputs>> for supported settings.

On first creation of a Coherence cluster, if your Maven or Gradle repository is empty, it may take a short while to download the minimal dependencies.

NOTE: These commands are experimental only and may be changed or removed in the future. It is *not supported* to use
these commands to create production clusters.

[#upgrade-local-clusters]
=== Upgrading existing clusters

Endpoint settings and the matching CLI REST URL are saved only after startup/readiness and a successful configuration write.
Start and restart reuse saved settings when endpoint flags are absent. Failed validation, cancelled confirmation, failed startup
or failed persistence retain the old saved settings and URL. A failed replacement after stopping a cluster leaves it stopped;
the CLI does not automatically restore the old running cluster. Stop works without Java and does not migrate old records.
Legacy records have no saved JMX port: their next start defaults to loopback REST with JMX disabled; specify `--jmx-port`
to enable JMX again. Existing running processes retain their old settings until restarted. Reverting to an older CLI may
restore the old exposure and ignore the new saved settings.

Restart requires a usable old-member snapshot from the saved REST URL, with a positive integer `clusterSize` matching
the number of distinct member PIDs. An unavailable endpoint, malformed response, empty snapshot, invalid member PID
or missing/inconsistent membership count stops restart before any stop or replacement. Failed discovery is not proof
that the old JVMs exited. Use `cohctl start cluster NAME` for an actually stopped cluster. Restart still trusts the
local PIDs reported by that REST endpoint; it does not maintain a PID registry or scan for undiscovered processes.

For the complete checklist, including SSH access, monitoring and TLS migration, see
xref:../about/upgrading_1_11_0.adoc[Upgrading from 1.10.14].

=== Common tasks

[source,bash]
----
cohctl create cluster local
cohctl get members -c local
cohctl stop cluster local
cohctl start cluster local --jmx-port 9999
----

The final command starts the stopped cluster with loopback JMX for JConsole or VisualVM.
For access from another machine, prefer the <<development-remote-access,SSH tunnel example>>.

*Creating and controlling clusters*

* <<create-cluster, `cohctl create cluster`>> - creates a local cluster and adds to the cohctl.yaml file
* <<scale-cluster, `cohctl scale cluster`>> - scales a cluster that was manually created
* <<stop-cluster, `cohctl stop cluster`>> - stops a cluster that was manually created or started
* <<start-cluster, `cohctl start cluster`>> - starts a cluster that was manually created
* <<restart-cluster, `cohctl restart cluster`>> - restarts a cluster that was manually created or started
* <<start-console, `cohctl start console`>> - starts a console client against a cluster that was manually created
* <<start-cohql, `cohctl start cohql`>> - starts a CohQL client against a cluster that was manually created
* <<start-class, `cohctl start class`>> - starts a specific Java class against a cluster that was manually created

*Setting dependency tool*

* <<set-use-gradle, `cohctl set use-gradle`>> - sets whether to use gradle for dependency management
* <<get-use-gradle, `cohctl get use-gradle`>> - displays the current setting for using gradle for dependency management

*Setting default heap sizes*

* <<set-default-heap, `cohctl set default-heap`>> - sets default heap for creating and starting clusters
* <<get-default-heap, `cohctl get default-heap`>> - gets default heap for creating and starting clusters
* <<clear-default-heap, `cohctl clear default-heap`>> - clears default heap for creating and starting clusters

*Creating and managing profiles*

* <<set-profile, `cohctl set profile`>> - set a profile value for creating and starting clusters
* <<remove-profile, `cohctl remove profile`>> - removes a profile value from the list of profile
* <<get-profiles, `cohctl get profiles`>> - displays the profiles that have been created

[#development-remote-access]
===== JMX and access from another machine

To enable the JDK JMX connector on loopback for a stopped cluster, alongside REST management:
[source,bash]
----
cohctl start cluster local -J 9999
----

Connect JConsole to `127.0.0.1:9999`. Both the registry and RMI connector use this port.
For access from another machine, keep the loopback defaults and use an SSH tunnel:

[source,bash]
----
ssh -N -L 127.0.0.1:9999:127.0.0.1:9999 -L 127.0.0.1:30000:127.0.0.1:30000 user@development-host
----

Connect JConsole to the forwarded local port. For REST, use `http://127.0.0.1:30000/management/coherence/cluster`.
Use the same local JMX port as the advertised port so the RMI stub follows the tunnel.

If you deliberately need insecure remote management on an isolated development network, select the bind addresses and
acknowledge the exposure on every invocation that starts a non-loopback listener:

[source,bash]
----
cohctl start cluster local --management-address 192.0.2.10 \
  -J 9999 --jmx-address 192.0.2.10 --jmx-host development-host.example \
  --allow-insecure-remote-management
----

Replace the documentation address with a real local interface. The CLI warns before launch, including with `--yes`.
The acknowledgement is never saved: subsequent start/restart needs it again, as does dynamic scale when it adds
non-loopback REST listeners. A wildcard REST bind stores `127.0.0.1` as the CLI destination, never `0.0.0.0`.
Authenticated remote JMX/REST and TLS provisioning are separate work; these commands are for development/testing only.

[#advanced-endpoints]
=== Advanced: endpoint selection

The bind flags `--management-address` and `--jmx-address` accept IPv4 literals or `localhost` (normalized to `127.0.0.1`).
DNS and IPv6 binds are unsupported. Use the concrete JMX bind as the advertised host, or explicitly set `--jmx-host`
for remote use. A wildcard JMX bind needs an explicit concrete advertised host. `--jmx-host` alone cannot make a
loopback listener remote. `--jmx-port=0` disables JMX and clears saved JMX address/host overrides.

[#advanced-lifecycle]
=== Advanced: startup, cancellation and dynamic listeners

During startup delay or readiness waiting, Ctrl-C (or SIGTERM on macOS/Linux) cancels the operation and stops
only members launched by that invocation. Existing members remain running during cancelled scale-up. Cancellation
before a stop pass leaves existing members untouched; once a stop pass begins, every listed member is attempted.
An interrupted restart cannot restore members already stopped. Previous saved settings and URL are retained until
startup is accepted for saving. If a signal arrives while settings are already being saved, a successful save completes
the operation. Successfully started members remain running after the command exits. During confirmation and dependency
resolution, interrupts retain their normal process-exit behavior; no new cluster members have been launched yet.

With `--dynamic-http`, create/start retain fixed REST on the first member and use ephemeral REST on later members.
Scale preserves its existing selection: the first added member has no REST listener and subsequent added members use
ephemeral REST. Every selected listener uses the chosen bind. Only the initial create/start member owns fixed-port JMX;
scale never adds another JMX connector. Scale accepts identical endpoint flags but requires restart to change endpoints.

[#advanced-jvm-options]
=== Advanced: JVM options and trusted inputs

Saved server arguments, the selected profile and `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS` and `JDK_JAVA_OPTIONS` cannot set
`com.sun.management.jmxremote` or its dot-qualified children, `com.sun.management.config.file`,
`com.sun.management.agent.class`, `java.rmi.server.hostname`, or the Coherence REST controls
`coherence.management.http`, `.http.address` and `.http.port`. The actual `tangosol.coherence.*` and `tangosol.*`
aliases of those Coherence controls are also reserved. The exact `coherence.management.config` key and its Coherence
aliases remain reserved pending release-specific consumer evidence. Use the endpoint flags for these settings.
Authentication/provider properties and `coherence.management` can pass through; this does not add authenticated REST
support or qualify a custom provider's listeners. Console and CohQL retain their client arguments.

Java/native agents, classpath and module-path options can pass through unchanged. Java checks their values and loads
user-selected code/resources. Saved managed arguments and profiles use CLI quoting; legacy saved arguments retain
literal space splitting. Environment options use matching quotes and ASCII whitespace, with literal backslashes and
non-ASCII text. The environment values are not rewritten. Environment agents also apply to the existing `java -version` check.
This lexical boundary is qualified only for the tested JDKs and locales.

The launcher accepts separate operands for `-cp`, `-classpath`, `--class-path`, `-p`, `--module-path`,
`--upgrade-module-path`, `--patch-module`, `--describe-module`, `-d`, and the five module options
`--add-opens`, `--add-exports`, `--add-reads`, `--add-modules` and `--limit-modules`.
Modular split forms require Java 9 or later; split `--enable-native-access` requires Java 17 or later.
These are parsing requirements, not vendor certification or a new global Java minimum. Long forms also accept an
attached `=value`. The VM-only variables `JAVA_TOOL_OPTIONS` and `_JAVA_OPTIONS` require attached forms;
`JDK_JAVA_OPTIONS` uses launcher operand rules. Empty classpath values are permitted in quote-aware sources.
Module names, packages, paths and their semantic validity are left to Java.

Uninspected option sources remain unsupported: raw leading-`@` tokens (including `@@`), `-XX:VMOptionsFile=`,
`-XX:Flags=` and `-Xoptionsfile=`. Direct `ManagementServer` and `-Xmanagement` switches are reserved.
Alternate launch targets (`-jar`, `-m`, `--module`, `--source` and their long attached forms), packed source-option
tokens and unclaimed bare operands are rejected before startup or restart stop. An unknown single option can pass
through, but its separate operand cannot be inferred. Use an attached spelling if the JVM supports it.
A parser pass is not proof of JVM support, successful startup or listener behavior. An unrelated invalid JVM value
can still fail after restart stops the old members.
